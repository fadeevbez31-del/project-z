# PROJECT Z — настройка панели администратора форума

## 1. Обязательная миграция Supabase

Открой Supabase → SQL Editor → New query. Скопируй **полный текст**
[admin_migration.sql](./admin_migration.sql) и выполни Run **один раз**.

Перед запуском сделай резервную копию схемы/данных. Скрипт добавляет поля
`pinned`, `locked`, `views`, `is_hidden`, таблицы жалоб, блокировок,
журнала, RLS-политики, защитные триггеры и RPC.

Проверь ограничения `profiles.role`: допустимые значения в этой версии
`player`, `vip`, `moderator`, `admin`. Если CHECK/enum в базе
разрешает меньше значений, обнови его отдельно с учётом текущей схемы.

После выполнения SQL обнови страницу форума Ctrl+F5.

## 2. Выдать первую роль администратора

В SQL Editor выполни запрос для **своего** аккаунта (замени email):

```sql
select id, email from auth.users where email = 'YOUR_EMAIL@example.com';
```

Потом (замени UUID):

```sql
update public.profiles
set role = 'admin'
where id = 'YOUR-USER-UUID';
```

Эту операцию выполняй в SQL Editor от владельца базы, а не через браузер.
При наличии защитного триггера миграции обновление роли напрямую может
быть запрещено — для первоначального назначения сначала выполни:

```sql
begin;
select set_config('app.forum_role_change','allowed',true);
update public.profiles set role='admin' where id='YOUR-USER-UUID';
commit;
```

После этого кнопка «⚙ Админ-панель» появится у админа после обновления.

## 3. Что доступно

- Статистика: количество профилей, тем, ответов, разделов, жалоб.
- Темы: закрепить/открепить, закрыть/открыть, переименовать, удалить.
- Пользователи: список, поиск по нику, изменение ролей, блокировка.
- Разделы: создать, переименовать, скрыть/показать, удалить пустой.
- Жалобы: отправка игроком и обработка администратором.
- Блокировки форума: просмотр и снятие. Заблокированным запрещено создавать
  темы и ответы на уровне триггеров Supabase.
- Журнал: кто выполнил административное действие и когда.
- SourceBans: ссылка на отдельную панель игровых банов.

**SourceBans не синхронизирован с форумными блокировками.** Игровые баны
остаются в SourceBans на bans.projectz.site. Для безопасной синхронизации
потребуется серверный API с отдельной авторизацией; никогда не размещай
MySQL пароль или service_role ключ в HTML/JavaScript.

## 4. Безопасность

- Административные изменения идут через `forum_admin_action`. Функция
  проверяет `auth.uid()` и роль `admin` в БД.
- Таблицы жалоб, блокировок и журнала защищены RLS.
- Защитные триггеры ограничивают изменение ролей и флагов тем.
- Никогда не доверяй одному лишь скрытию кнопок в интерфейсе.
- **Важно:** миграция добавляет политики, но не удаляет старые широкие
  RLS-политики. Проверь существующие политики на `profiles`,
  `forum_topics`, `forum_replies`, `forum_categories`, особенно
  `INSERT`/`UPDATE`/`DELETE`. Админские действия через RPC
  защищены, но слишком широкие старые политики могут допускать обход
  для незащищённых операций.
- Счётчик просмотров приблизительный: браузер считает один просмотр за
  сессию; это не уникальные посетители и не защита от накрутки.
- Тестируй после миграции под админом и обычным игроком.

## 5. Возможные ограничения

- Список пользователей и тем пока ограничен 100 последними записями;
  расширение требует пагинации.
- Скрытие раздела в текущем интерфейсе не делает его содержимое
  конфиденциальным: если нужна приватность, требуются отдельные RLS
  политики на чтение тем и категорий.
- Список ролей может требовать адаптации к CHECK/enum вашей БД.
